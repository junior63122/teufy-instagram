PARTIE 6 — SUPPRIMER LES FAUSSES VALIDATIONS ET LES RÉSULTATS BIAISÉS
C'EST UNE PRIORITÉ ABSOLUE.
Je ne veux plus qu'un bot indique qu'une tâche est réussie alors qu'elle n'a pas réellement fonctionné.
Je ne veux plus de résultats présentés comme positifs simplement parce que le programme n'a pas rencontré d'erreur apparente.
Je ne veux plus de tests biaisés qui valident automatiquement des opérations incomplètes.

1. Nouveau système de vérification
Chaque opération importante doit être vérifiée à plusieurs niveaux :
Niveau 1 — Exécution : le bot a-t-il réellement exécuté l'action ?
Niveau 2 — Réponse technique : le système ou l'API a-t-il confirmé la réception et le traitement de la demande ?
Niveau 3 — Résultat effectif : le résultat attendu est-il réellement observable via une source fiable ?
Niveau 4 — Vérification indépendante : un mécanisme distinct peut-il confirmer que l'opération a produit le bon résultat ?
Une simple réponse HTTP 200 ou un message de succès interne ne suffit pas à prouver que l'opération finale est réussie.

2. États de validation explicites
Chaque opération doit posséder un état fiable :
• SUCCESS_VERIFIED : résultat effectivement confirmé.
• PENDING_VERIFICATION : action lancée, résultat non encore confirmé.
• FAILED : échec confirmé.
• PARTIAL_SUCCESS : résultat incomplet.
• UNKNOWN : impossible de déterminer le résultat.
• BLOCKED : action empêchée par une dépendance ou une autorisation.
Interdiction de convertir automatiquement un résultat UNKNOWN ou PENDING en SUCCESS.

3. Tests anti-faux-positifs
Crée des scénarios destinés spécifiquement à tromper les mécanismes de validation actuels.
Par exemple :
• Une API répond positivement, mais l'action finale échoue.
• Une réponse est incomplète.
• Une requête expire.
• Une action est dupliquée.
• Une donnée ancienne est interprétée comme une nouvelle donnée.
• Une publication semble envoyée mais reste non confirmée.
• Une dépendance est indisponible.
• Une réponse technique contient des données incohérentes.
• Un test réussit avec un faux service mais échoue en intégration réelle.
• Un bot se valide lui-même alors que sa logique est défectueuse.
Corrige les failles de validation détectées.

4. Éviter les analyses biaisées
Je veux des résultats objectifs.
Pour cela :
• Sépare le système exécutant les tâches du système qui vérifie les résultats.
• Utilise des jeux de tests indépendants.
• Ajoute des cas négatifs.
• Introduis des données volontairement incorrectes.
• Vérifie les cas limites.
• Mesure les faux positifs et les faux négatifs.
• Conserve des preuves exploitables.
• Compare les résultats attendus aux résultats réellement constatés.
• Vérifie que les tests peuvent effectivement échouer lorsqu'une anomalie est présente.
Ne te contente pas de créer des tests qui confirment ce que tu as toi-même développé.

PARTIE 8 — LES 10 CYCLES OBLIGATOIRES
Tu dois maintenant réaliser les 10 cycles suivants.
Chaque cycle doit obligatoirement analyser à nouveau le site ET les bots Instagram, même lorsqu'un sujet particulier est prioritaire.
CYCLE 1 — Audit général : analyse intégralement les sites, les parcours utilisateurs, les automatisations Instagram et les dépendances techniques. Corrige les défauts majeurs.
CYCLE 2 — Expérience utilisateur : exécute les scénarios correspondant aux 1 000 profils définis, avec une couverture explicite des parcours et comportements. Analyse les difficultés observées, puis améliore les interfaces.
CYCLE 3 — Ergonomie et fluidité : optimise la navigation, les formulaires, les temps de réponse, les interactions et les parcours. Recherche les étapes inutiles.
CYCLE 4 — Qualité visuelle : effectue une inspection graphique complète. Corrige les incohérences, les problèmes d'affichage et les défauts de responsive.
CYCLE 5 — Fonctionnalités manquantes : recherche toutes les fonctionnalités, automatisations et améliorations utiles qui n'ont pas encore été envisagées. Implémente les plus pertinentes.
CYCLE 6 — Performance des bots Instagram : réanalyse chaque bot, identifie les ralentissements et les processus inefficaces. Optimise les performances et la qualité des résultats.
CYCLE 7 — Fiabilité des validations : teste intensivement les mécanismes de validation. Recherche les faux succès, les résultats biaisés et les erreurs silencieuses. Introduis des contrôles réellement indépendants.
CYCLE 8 — Sécurité et stabilité : effectue un audit complet des vulnérabilités potentielles, des accès, des API et de la gestion des données. Corrige les problèmes confirmés.
CYCLE 9 — Tests extrêmes et régressions : recherche volontairement les situations pouvant provoquer des erreurs. Teste les cas limites, les changements de comportement, les interruptions et les enchaînements inhabituels. Relance les tests utilisateurs et les tests des bots après correction.
CYCLE 10 — Contre-audit final indépendant : recommence une analyse complète comme si tu découvrais le projet. Remets en question toutes les améliorations précédentes. Teste à nouveau les fonctionnalités et les validations. Corrige les derniers problèmes reproductibles.

PARTIE 9 — MÉTHODE DE TRAVAIL OBLIGATOIRE
Pour chacun des 10 cycles :
ÉTAPE A — ANALYSER : examiner le système concerné en profondeur et rechercher de nouveaux défauts.
ÉTAPE B — CRITIQUER : identifier les problèmes, les fonctionnalités manquantes, les risques et les mauvaises décisions techniques.
ÉTAPE C — PRIORISER : classer les améliorations selon leur gravité, leur impact et leur complexité.
ÉTAPE D — CORRIGER : modifier concrètement le code et les configurations nécessaires.
ÉTAPE E — TESTER : effectuer des tests réels, automatisés et indépendants lorsque les outils le permettent.
ÉTAPE F — CONTRE-VÉRIFIER : faire vérifier les résultats par un mécanisme distinct de celui ayant réalisé l'action.
ÉTAPE G — NOTER : attribuer des notes sur 100 pour : expérience utilisateur, design, navigation, rapidité, fonctionnalités, stabilité, sécurité, accessibilité, performance des bots, précision des bots, fiabilité des validations, couverture des tests. Utilise des critères mesurables, indique les limites des mesures et n'attribue aucune note artificiellement.
ÉTAPE H — RECOMMENCER : passe au cycle suivant, même si les résultats semblent excellents.

PARTIE 10 — CONTRÔLE QUALITÉ ET ABSENCE DE RÉGRESSION
Chaque nouvelle modification peut créer des problèmes ailleurs.
Je veux donc un contrôle automatique de non-régression.
Après chaque modification importante :
1. Exécute les tests unitaires concernés.
2. Exécute les tests d'intégration.
3. Vérifie les parcours utilisateurs critiques.
4. Contrôle les fonctionnalités Instagram concernées.
5. Vérifie les sorties et les statuts des bots.
6. Contrôle les erreurs serveur et navigateur.
7. Vérifie les performances.
8. Compare les résultats aux versions précédentes.
En cas de régression, corrige-la avant de valider le changement.
Conserve des points de restauration et un historique des modifications.
Ne modifie pas les systèmes en production de manière risquée sans environnement de validation adapté.

PARTIE 12 — OBJECTIF DE QUALITÉ
Je veux viser un niveau de qualité de 99/100 minimum sur tous les domaines évalués, avec l'objectif d'atteindre 100/100 sur la réussite des scénarios de tests critiques.
Mais attention : tu n'as pas le droit de truquer, d'adapter ou d'assouplir les tests simplement pour obtenir ces notes.
Je préfère que tu annonces objectivement 91/100 avec des preuves plutôt que 100/100 sans réelle vérification.
Aucun bot ne doit être déclaré parfaitement fiable sans éléments suffisants.
Aucune fonctionnalité ne doit être déclarée validée si elle n'a pas été réellement testée.
Aucune simulation utilisateur ne doit être présentée comme un véritable test humain.
Aucune absence d'erreur ne doit être interprétée automatiquement comme une réussite.
La fiabilité des résultats est plus importante que leur apparence positive.
